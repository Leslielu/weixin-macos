## 1. 静态分析定案(反汇编结论, 已实证)

### 1.1 身份换位: req2buf 三件套全死, 真入口 = SubmitCgi

- `req2bufEnterAddr`(旧 Req2Buf 入口)在 4.1.13 = **SubmitCgi(0x42e3450,
  mgr, msg)**: 一次调用原生完成 lock(mgr+0x80) → Task ctor(结构 0x1A0→**0x218**
  涨了) → URI 串拷贝 → AutoBuffer ctor(0x4308a9c) → **经 msg->vt+0x10(msg, ab)
  虚调用做序列化分发** → StartTask → taskid 写回 msg+8 → 红黑树原生 insert → unlock。
- `req2bufExitAddr`(0x42e39c0)= SubmitCgi 尾部, `buf2RespAddr`(0x430783c)
  身份换位, 两者零触发实证已死。`sendFuncAddr`(MMStartTask) V3 不再 replay。
- 旧 replay 范式死因(= 手写 insert / MMStartTask 重放两代尝试):
  Task 模板 0x1A0→0x218 过期, errType=7 本地否决; manager 消费者改 find-and-pop。
- H = 完成回调 consumer(头 0x42e48dc): found 路径 `ldr x22,[x25,#0x28]`
  装载 msg, 之后 ① `msg->vt+0x18(msg, ab)` 响应分发; ② `cb=msg+0x68`,
  `cb->vt+0x30(cb,…)` 完成回调; **完成回调返回 0 ⇒ H 跳过 msg 析构**。
- **入口禁区**: SubmitCgi 函数体内部指令点 hook 即崩(见铁律2); 入口(第一条
  指令)hook 是 Interceptor 标准函数头重定位, 整晚安全。

### 1.2 msg 结构(运行时 realmsg/submitProbe dump, 5 次采样)

```
+0x00 vtable        (专用虚表: +0x10 序列化, +0x18 响应)
+0x08 taskid        传 0, SubmitCgi 分配后写回
+0x0c cmdid         0x20a=文本 newsendmsg, 0x6e=sendappmsg 类
+0x10 selector      观测恒为 1 (4.1.11 的 3 是旧范式值, 不可跨版)
+0x18 URI 老libc++长串 {ptr,size,cap} + 0x2f 长串旗标 0x80
      (SubmitCgi 拷贝构造只读 ptr/size, cap 照抄观测值)
+0x30 flags = 0x01010100 (发送类实证; +0x31=1, +0x32=0x0101)
+0x38..0x4f 合法空串(全零=短串size0)
+0x40..0x47 = 00 00 00 00 01 00 00 00 (原生稳定字节照抄)
+0x68 cb 回调对象指针 (NULL ⇒ H 尾 __cxa_throw 硬崩, 15:13 实锤)
```

### 1.3 AutoBuffer 家族(4.1.13 语义未变, dryrun 验证)

ctor 0x4308a9c / write 0x4308c58(ab, data, len) / data 0x4308d08 / len 0x4308cfc。
读法双重解引用: `D=ab.readPointer(); dataPtr=D.readPointer(); len=D.add(0xc).readU32()`。

### 1.4 JSON 键变化(structVer "3")

新增 `mgrCaptureAddr`=0x42e4c2c(捕获 manager x19), `respDispatchAddr`=0x42e5044
(收发统一响应分发)。`blrX8Addr`=0x42e3540 仅存档(V3 不 hook, 见铁律2)。
req2bufEnterAddr 语义变为 SubmitCgi 入口(call-only + read-only 入口探针)。

### 3.1 现象(存档)

22:53:32 出队调 SubmitCgi → taskid=345 写回 → 日志正常打印 → **消息已送达
用户** → ~1s 后微信进程死亡(session detached reason=4), dump:
`WeChat-4.1.13_c27987a2`(22:53)。即: 崩溃发生在**任务完成路径**, 不在提交路径。

### 3.2 嫌疑排序与思路

1. **completeCb NativeCallback 签名不匹配(头号嫌疑)** [推断]
   完成路径 `cb->vt+0x30(cb,…)` 是整条发送链上**最后一个 NativeCallback**,
   签名(4 指针)是猜的。H 实际传参若不同, NativeCallback 编组会读错栈 →
   在微信线程上产生不可捕获的崩溃。时间线吻合: 崩溃 ≈ 网络往返 1s 后 =
   响应到达、完成回调触发的时刻。22:53 之前它从未被真正执行过(所有更早的
   尝试都死在提交路径), 所以"完成回调 NativeCallback 安全"从未被验证。
2. H 尾读伪造 msg +0x68 之外的未映射字段 [次要] — +0x38..0x4f 已清成合法
   空串, 但真 msg 在 +0x50..0x78 还有数据, 若完成路径解引用即崩。
3. msg 析构判定 [次要] — 完成回调返回 0 ⇒ H 跳过析构(§1.1), 若该解码有误,
   微信 delete 我们的 frida 堆对象即崩。

### 3.3 修复(✅已验证生效)

## 4. 四条蹦床铁律(2026-09-20 实锤×6, 跨版本通用)

1. **NativeCallback 不得出现在 native 虚调用路径上**。JS 已进入线程经
   NativeFunction 调用再被 native 虚调用回调 = 确定性 AV@0x4/0xa(×3, 线程无关)。
   即便纯 native 上下文触发, 签名是猜的也会崩(22:53 完成路径, 见 §3)。
2. **SubmitCgi 函数体内指令点不可 hook**(入口可以, 整晚安全)。体内 hook 的
   重定位破坏原生热路径(22:17)。需要介入序列化 ⇒ 全部改走 msg 虚表。
3. **Memory.alloc+patchCode 自有页不得作为 native 虚调用目标**。JS 线程可执行
   (自检通过)但微信线程 blr 必 AV@页地址(22:35 rw- / 22:43 r-x 同址两杀) —
   自有页执行权存在线程级门槛, 提权救不了。
4. **frida 自家 code allocator 页是唯一可信自有执行区**(Interceptor trampoline /
   CModule)。所有 read-only hook + CModule stub 整晚被微信线程执行无恙。
   ⇒ 一切需要被 native 调用的自有代码 = CModule。
5. **(运维, 2026-09-21 08:48 实锤) 禁止对存活微信 kill onebot 换脚本**。
   kill onebot = gadget 会话拆除, 崩溃线程 `frida-gadget-tcp-27042`、帧全在
   FridaGadget.dylib 拆除路径(与我们的 hook/JS 无关, 当时连 SubmitCgi 都没
   调)。拆除是竞态轮盘赌: 同样的 kill 08:46 活了、08:48 崩了。
   **换脚本 = 微信+onebot 同步重启**。

## 5. 工具与方法论教训

- **dmpparse.py 有 bug, 勿信其寄存器级输出**: 两个不同时间戳的 dump 解析出
  完全相同输出(含跨进程相同的线程 id 117270053)——不可能。当晚所有基于 dump
  的寄存器结论作废, 主线结论全部有日志证据支撑。修复 dmpparse 或换
  lldb/IDA 分析 dump 后再恢复使用。
- **QuickJS(gadget 17.5.2) CModule 三坑**:
  1. 函数导出是纯 NativePointer, 不能直接调用 — 须 `new NativeFunction(cm.f,...)`
     包装; writePointer 则直接用指针;
  2. CModule 页 r-x, JS 侧写 C 全局 = AV —— per-send 数据改走"邮箱":
     放在 JS 侧 rw- 的假回调对象里(cb+0x08=dataPtr, cb+0x10=len),
     C stub 经 msg+0x68→cb 读取;
  3. 编译失败/自检失败只禁用发送, 不抛异常 —— 收消息不陪葬。
- **渲染检查模板**(BSD sed 不行, 用 perl):
  `perl -pe 's/\{\{if \.\w+\}\}//g; s/\{\{end\}\}//g; s/\{\{\.\w+\}\}/0x1000/g; s/\{\{\.structVer\}\}/"3"/g' onebot/script.js > /tmp/r.js && node --check /tmp/r.js`
- **gadget 会话预算 ~9 次/微信生命周期**(09-21 实测), 超了控制通道 wedge:
  脚本只打出模块基座行就死, 重试无输出, 唯一解 = 重启微信重登。
  且 kill onebot 拆会话本身可崩宿主(铁律5) ⇒ 会话预算更要省着用。
- **frida 17 API 删减**: 静态 `Module.getExportByName` 不存在(TypeError),
  取符号用回退链 `Module.getGlobalExportByName` → `Module.findExportByName`
  → `Process.getModuleByName("libsystem_kernel.dylib").getExportByName`。
- **0x33 malloc zone 铁律(09-21 两处同坑)**: `Process.findRangeByAddress`
  对 `0x33_xxxx` zone 不可见 → IfReadable 门控助手全数误报"不可读"。
  上午吞 CDN 钥匙(cndOnComplete), 下午吞全部发送 ack。**该 zone 唯一正确
  读法 = 裸读 + try/catch**; 门控助手只用于普通 zone(收消息路径实测可用)。
- **毒锁后唯一恢复 = 重启微信**; 每次毒锁丢一次登录, 慢慢来。
- 引用消息测试法: 从 onebot 日志 `发送数据 msg=` 行取原始 WechatMessage
  (Go %q 转义, 需双重 json.loads 还原), 整个对象回传 `reply_message` 即可,
  msgsource/signature 都在其中。
