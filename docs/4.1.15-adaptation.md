## 4. 接收丢失: 排查全程（含重大反转）

**症状**: 发送侧全通（ack 全命中），接收侧 UI 正常显示，但 onebot 收不到用户消息。

**排查链（按时间，含结论反转）**:
1. 低级错误排除: 容器账号目录确认 dev 登录 ✓；onebot wxid ✓；发送 ack ✓。
2. OnPush 无条件计数器 DIAG: 零日志 → **误判** "OnPush 没被调用"（见步骤6反转）。
3. 静态验证 __OnPush 身份: `task push name:%_` 全库唯一引用点就在所挂函数内，
   注册点 adrp+add 引用两版各一个且相对结构一致 → 函数在、注册在。

   → 回查 session2: **13 条同样错误**。DIAG 用了 `typeof X === "undefined" { X = 0 }`
   守卫——**strict mode 下给未声明变量赋值直接抛 ReferenceError，onEnter 第一行即死**。
   错误时间点遍布全程 = **这些会话里的 OnPush onEnter 确实被调用过**，只是被带毒
   DIAG 杀了观测；它不能证明干净 session6 的聊天仍走 OnPush。
7. **当时推断（后被收敛）**: session1（无这批毒 DIAG）里，用户回复的时间点（22:09:01/

   因而怀疑 Go 的 `parseAllRecvData` 固定 wrapper→body→content.data 链不适配。
   后来 hexdump 证明部分 WARN 只是 ambient 同步控制包；当前“拔毒 DIAG + 递归兜底”
   组合已让聊天接收通过，但**没有单独 A/B 出递归兜底是否必需**，不得再写成已证实
   “4.1.15 聊天信封必然改形”。
8. 附带损伤: 带毒 DIAG 的还有 resp-dispatch receive 分支（v3RspDiagN 同款写法）——
   session2-4 里 resp-dispatch 收包路也被第一行 ReferenceError 杀死。llSRH 的
   DIAG（v3SrhDiagN 用 var 声明）是唯一合规的，所以只有它能打出日志。

## 7. 文档纠错清单（本次发现，收尾时回写）

1. `docs/version-upgrade.md` 语音通话地址迁移节: 「搜 0x2e6981b3 立即数拼装序列」

## 8. 复盘: 走过的弯路（下一版别重蹈）

1. **带毒 DIAG 污染观测**: 最大弯路。两轮 restart 花在验证一个被观测代码杀死的路径。
   教训: DIAG 上线后先看有没有 `[JS日志报错]`，**先证明观测代码本身活着再信它的产出**。
2. **收消息问题先怀疑"架构大变"**: 用户提醒先查低级错误是对的——账号/容器/基址
   排除虽未直接命中，但"发送 ack 正常+UI 正常"本就暗示捕获层小毛病而非大迁移。
3. **魔数静态搜索**按文档硬扫两轮才证伪——文档与历史事实不符时应先查发现记录
   （probe 脚本/git log）再硬扫。
4. **llSRH 内部零 blr** 后想扫全 __TEXT 找 vtable walker——被注册点反汇编直接替代。
5. **ADRP+ADD 字节级引用扫描**（/tmp/wx4115/ 内联脚本）值得固化进 `tools/addrfind/`
   （strxref.py 不支持 conf 小切片和任意目标地址场景）。
6. **一轮不要同时改多个变量再宣布根因**: 接收恢复那轮同时拔毒 DIAG、加 Go 递归
   兜底、换 srh 观察点，结果虽通过，却无法分别证明哪项必需。收尾必须补最小 A/B，
